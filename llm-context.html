大模型的上下文（Context）

概念英文：Context Window / Prompt Context ｜ 适用场景：提示词工程、长文档问答、RAG

1一句话定义

上下文就是大模型在生成回答时，眼前能看到的全部文字，长度有限（这个上限叫"上下文窗口"）。

2核心直觉 / 为什么需要它

  • 没有它之前：模型每次只能"看一句话"，回答完就忘了前文，做不到多轮对话，也读不了长资料。
  • 它解决的根本问题：把系统提示、对话历史、参考资料、工具返回全部"摆"在模型面前，让它基于完整信息做判断。
  • 核心思想（一句话）：有限的"工作台面"——东西太多就放不下，必须学会取舍与压缩（截断 / 摘要 / 检索）。

3生活化类比

像你的办公桌桌面：桌面就那么大，能同时摊开的文件有限。要处理新文件，就得把旧的归档或清走；重要的钉在"便签"（系统提示）上永远留着。

对应关系：桌面大小 = 上下文窗口（token 数）；摊开的文件 = 当前拼进提示的词；清走旧文件 = 滑动窗口/截断；去档案柜取 = 检索增强（RAG）。

4工作机制（逐步拆解）

  1. 放系统提示：最前面放 System Prompt（角色、规则），始终占着"桌面"。
  2. 拼装内容：按"系统 → 历史对话 → 参考资料 → 工具返回"的顺序拼接文本。
  3. 调用工具：工具返回的结果也写回上下文，成为后续思考的一部分。
  4. 超限处理：总长度超过窗口时，截断早期内容、做摘要，或用检索只取相关片段。
  5. 生成：模型基于"整个窗口"逐词（token）预测下一个输出。
  6. 滚动：多轮对话中，旧内容被挤出窗口，保证最新上下文始终在限内。

5代码示例（Python 3.12，可直接运行）

# context_window.py —— 管理"上下文窗口"长度，超长就截断
def truncate_to_budget(text: str, max_tokens: int,
                       chars_per_token: float = 4.0) -> str:
    # 用"字符数/4"粗略估算 token 数（中文约 1~2 字/token，这里取近似）
    budget_chars = int(max_tokens * chars_per_token)
    if len(text) <= budget_chars:
        return text
    keep = text[:budget_chars]
    return keep + "\n…[已截断，超出上下文窗口]"

ctx = "系统：你是课程助教。\n" + ("用户：请解释 Transformer 的原理。\n" * 500)
print(f"原始长度 {len(ctx)} 字符")
safe = truncate_to_budget(ctx, max_tokens=2000)
print(f"裁剪后 {len(safe)} 字符，可安全塞进上下文窗口")

运行后能看到"超长文本被裁剪到预算内"。真实系统还会配合 embeddings 检索，只把相关片段放进窗口。

6自测练习（3 题）

Q1 概念复述：请用一句话说明"上下文窗口"是什么，以及为什么它很重要。
参考答案
上下文窗口是模型一次能"看到"的最大文本量（token 上限）；它决定了模型能记住多少历史、能读多长的资料，是长对话和长文档处理的天花板。
Q2 机制辨析：判断正误：把 10 万字的书全文塞进提示词，模型就一定能准确回答关于这本书的任何问题。
参考答案
错误。受上下文窗口限制，全文往往放不下；硬塞会截断或超出限制。正确做法是检索（RAG）只取相关段落，而非全文塞入。
Q3 应用迁移：多轮聊天里，最早的一条消息被"挤出"窗口后，模型是不是就彻底忘了它？有什么办法缓解？
参考答案
模型当下确实"看不到了"，但可用两类办法缓解：①把关键信息周期性摘要后写回系统提示；②把历史存入外部记忆（数据库/向量库），需要时检索注入。即"忘在眼前，记在别处"。
